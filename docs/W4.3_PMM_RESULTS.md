# W4.3 controlled allocator measurement — 2026-10-07

The page allocator now has a controlled one-worker/four-worker baseline. No
allocator code or cache tuning was changed. This follows the
[FD reference checkpoint](W4.3_FD_RESULTS.md) on the same combined kernel.

The static musl probe runs persistent fork workers with independent memory and
FD tables. It pins them to distinct requested CPUs, checks actual CPU placement
before and after touch and before unmap, and repeats eleven rounds: one discarded
round and ten measured. Every worker maps 16 MiB, checks zero bytes on all 4,096
pages, writes a deterministic per-page marker, verifies the checksum and checks
the contents again after the held-mapping barrier. Unmap and every child exit
are checked. Private command/response pipes provide parked before/held/after
barriers; worker/round and independent host deadlines bound execution.

All mappings remain live during the held snapshot. Parent samples real MemFree
and weighted buddy block counts before allocation, while mappings are held, and
after all workers unmap. The complete ordered protocol has 55 worker records and
66 snapshots. The runner checks environment, counts, CPU identity, contents,
positive phase times, metadata status/arithmetic and exact barrier record order.
A separate review found two validator gaps, both fixed before guest tests; 10
corrupted variants of a real valid Linux log are rejected. Missing host metadata
is explicit; complete guest metadata is required for this measurement.

Configuration: q35 BIOS, four vCPUs, 1536 MiB; KVM host CPU or multithreaded TCG
max with rdrand/rdseed. Single-worker control still runs in a four-vCPU guest.
Measurements were isolated from other QEMU runs. Both KVM and TCG completed
55/55 checks, as did each Linux reference run. Invalid CPU selection was rejected;
SIGTERM at a held-mapping checkpoint failed the workload and reaped its workers. Timers reported 1 ns on Linux/KVM
and 10 ns on TCG. No fatal allocator diagnostic or allocation failure occurred.

Each repetition contributes the maximum individual worker duration. Independent
worker timers do not measure total group makespan or aggregate throughput. The
map+touch measurement includes AzamiOS's eager allocation; Linux may allocate
during first touch. These are mapping latency baselines, not pure PMM-lock cost,
page-fault counts, or physical-machine throughput claims.

The retention column is an **approximate cross-read estimate**. AzamiOS's
MemFree includes per-CPU cached pages, while buddyinfo reports only buddy lists.
Background allocation and the two separate reads can move the difference, even
make it negative. It does not identify which CPU retained pages or establish
exact PCP ownership. Parked workers reduce workload movement but do not make
procfs reads an atomic snapshot. No cumulative leak is inferred from these
within-run differences.

Four held maps consume 64 MiB and leave ample free memory. This does not test
near-exhaustion starvation, mixed-order/DMA allocation, remote-cache reclaim,
refill/drain counts, or native hardware behavior. The source audit confirms
ordinary allocation failure drains only the caller's PCP cache, while free
totals include remote caches. Measure those failure and mixed-order paths with
explicit counters before changing the existing 128-page cap/64-page batch or
adding cross-CPU reclaim. User-copy and COW/range shootdown measurements remain
other W4.3 work.
